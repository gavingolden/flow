# Company report generation (`POST /reports`)

**Goal:** A caller submits a company name and, within minutes, can fetch a five-section report that survives restarts, never double-charges on retry, and stays within a daily spend cap.

## Problem Statement

The reports service exists to hand out company reports, but nothing can create one today: it can only fetch and share reports, and no report ever gets into its store. Writing a report takes five paid model calls of 20 to 60 seconds each, so a caller who waits for the finished report waits up to five minutes. The platform also cuts requests off at five minutes. If the work runs inside the request, a slow day fails the request, a retry pays for all five sections again, and anyone on the internet can start paid work, because the service is deployed without authentication.

Evidence:

| Fact | Consequence | Anchor |
| --- | --- | --- |
| Each section call "Takes 20-60 s per call and costs money per call" | 5 sequential calls = 100–300 s; 5 parallel calls ≈ 60 s. Both are far past the 10 s interactive budget | src/llm.ts:1 |
| The model call has no timeout and never checks the HTTP status | a hung or failed upstream call hangs the handler or stores `undefined` as section text | src/llm.ts:6-10 |
| Reports live in a process-local `Map` | lost on every deploy or scale-to-zero; a second instance cannot see them | src/db.ts:9 |
| The service deploys with `--allow-unauthenticated` | any caller can trigger paid generation | deploy.sh:3 |
| Cloud Run's request timeout defaults to 300 s; CPU is throttled after the response under request-based billing | inline generation can be killed mid-run; background work after a 202 on the same instance stalls | https://docs.cloud.google.com/run/docs/configuring/request-timeout, https://docs.cloud.google.com/run/docs/configuring/billing-settings |
| `Report` already has `company`, `sections: string[]` and a nullable `title` | the stored shape already expects multi-section reports; no title is required | src/db.ts:1-7 |

Measured against the product brief's ranked priorities, the stakes are **user experience** (no multi-minute blocking wait, no lost reports) and **cost** (no paid call repeated by a retry, a hard ceiling on daily spend).

## Request vetting

- **Hypothesis:** Five paid section calls can run behind a `POST /reports` that answers within the 10 s interactive budget, with each section finished at most once and total spend capped per day.
- **Case against:** Read literally, "a `POST /reports` endpoint that generates a company report by calling the model API" means the handler makes the calls and returns the report. At 20–60 s per call that is 100–300 s sequential, it meets Cloud Run's 300 s default timeout, and any client retry pays for all five calls again [anchor: src/llm.ts:1]. The in-memory store cannot hold the work across instances either [anchor: src/db.ts:9].
- **Sources:** https://docs.cloud.google.com/run/docs/configuring/request-timeout ; https://docs.cloud.google.com/run/docs/configuring/billing-settings ; https://www.rfc-editor.org/rfc/rfc9110#name-202-accepted
- **Verdict:** push back: `POST /reports` accepts the request and returns `202` with a pollable report id, and the five paid section calls run as one queued task each on an authenticated worker, against a durable store and one daily spend cap

## Existing-code assessment

- **src/app.ts (router + handlers):** keep — the regex-route `handle(req)` shape fits two more routes; it gains injected dependencies and a role switch for the worker [anchor: src/app.ts:9]
- **src/db.ts (persistence):** rewrite — a process-local `Map` cannot be shared by the API and the worker or survive a restart, so the durable store is a prerequisite and a bundled task (Tasks 3–4) [anchor: src/db.ts:9]
- **src/llm.ts (model client):** simplify — keep both functions, but add an explicit timeout, a status check and a typed error so the worker can tell transient failures from permanent ones (Task 1) [anchor: src/llm.ts:6-10]
- **deploy.sh (deploy):** keep — extend the one `gcloud run deploy` into two services (public API plus a private worker) with instance caps [anchor: deploy.sh:3]

## Scope Boundary

**In scope:**

- `POST /reports` with body `{ "company": string }`: authenticated with an API key, honours an optional `Idempotency-Key`, returns `202` with a `Location: /reports/{id}` header.
- A fixed list of five section names. Each section is generated by one queued task that calls the model once per attempt.
- `GET /reports/{id}` gains `status` (`queued | running | partial | failed | done`) and per-section progress, readable while generation runs.
- A durable store (Firestore) replacing the in-memory map, with point-in-time recovery, daily backups and a restore check.
- One daily spend cap on section calls, enforced at a single choke point. Setting the cap to `0` doubles as the kill switch.
- Hardening the model client: a timeout, a status check and failure classification.
- Metrics helper plus `.flow/metrics.md`, a queue with retry and rate settings, a private worker service, and a rollback script.

**Out of scope:**

- Generating a title (`suggestTitle`). Reports keep `title: null` (see Open Questions).
- Caller-chosen section lists, streaming tokens or SSE progress, and webhooks on completion.
- A user or ownership model, and authentication on the existing read and share routes.
- Report retention and deletion policy.

## Behavioral contrast

### User flow

| Before | After |
| --- | --- |
| No way to create a report. `GET /reports/{id}` always returns 404 because nothing writes reports | `POST /reports {"company":"Acme"}` with an API key returns `202` and a report link in under 2 s |
| — | Polling the link shows `queued → running → done` (or `partial` with the sections that failed marked) within a few minutes |
| — | Re-sending the same request with the same `Idempotency-Key` returns the same report and is not charged again |
| — | A request past the day's spend cap gets `429` with `Retry-After` and is not charged |
| Reports (if any existed) vanished on every deploy | Reports survive deploys, restarts and scale-to-zero |

### System flow

- **Before:**
  - A single public Cloud Run service with no auth holds reports in process memory.
  - The model client has no caller and no timeout.
- **After:**
  - The public API writes a report row plus five section rows to Firestore, then enqueues five named Cloud Tasks (`<reportId>-<section>`).
  - A private worker service (IAM-only; only the queue's service account may invoke it) claims a section, reserves one unit of the daily cap, calls the model with a 90 s timeout, then writes the text or a failed state.
  - Retries happen only in the queue (max 4 attempts). The report's status is derived from its sections when read.

**Lost:** none — the change is additive. The existing `GET` and share routes keep their paths and fields (new fields are added only), and the in-memory store held no surviving data.

## User Stories / Acceptance Criteria

### Story 1: Start a report

- [ ] Given a valid API key and `{"company":"Acme"}`, when the caller `POST`s `/reports`, then the response is `202` with `Location: /reports/{id}` and body `{ id, status: "queued" }`, and exactly five section tasks are enqueued. Check: `bun test src/app.test.ts` ("creates report and enqueues five sections").
- [ ] Given a missing or wrong API key, when the caller `POST`s, then `401` is returned and nothing is stored or enqueued. Check: `bun test src/app.test.ts` ("rejects unauthenticated").
- [ ] Given an empty, non-string or over-200-character `company`, when the caller `POST`s, then `400` is returned. Check: `bun test src/app.test.ts` ("validates company").
- [ ] Given the same `Idempotency-Key` and body sent twice, then both responses carry the same report id and only five tasks exist. Given the same key with a different body, then `422` is returned. Check: `bun test src/app.test.ts` ("idempotency").
- [ ] Given today's remaining cap is below 5 section calls, when the caller `POST`s, then `429` with `Retry-After` is returned and no report is created. Check: `bun test src/app.test.ts` ("budget exhausted").

### Story 2: Sections generate exactly once and fail visibly

- [ ] Given a queued section, when the worker receives its task, then it calls the model once, stores the text and marks the section `done`. A redelivered task for a `done` section returns `200` with no model call. Check: `bun test src/worker.test.ts` ("idempotent redelivery").
- [ ] Given a model timeout or a `429`/`5xx`, when the attempt is not the last, then the worker returns `503` so the queue retries. On the last attempt (`X-CloudTasks-TaskRetryCount` = max − 1) the worker marks the section `failed` and returns `200`. Check: `bun test src/worker.test.ts` ("transient then final").
- [ ] Given a `4xx` other than `429`, or a malformed model response, then the section is marked `failed` on the first attempt with no retry. Check: `bun test src/worker.test.ts` ("permanent failure").
- [ ] Given the daily cap is exhausted at call time, then no model call is made and the section is marked `failed` with `budget_exhausted`. Check: `bun test src/worker.test.ts` ("cap at choke point").
- [ ] Given a request without the worker role (the public service), when anything hits `/internal/section-tasks`, then `404` is returned. Check: `bun test src/app.test.ts` ("worker route not on api role").

### Story 3: Read progress

- [ ] Given a report with 3 sections done and 2 running, when the caller `GET`s it, then `status` is `running`, `sectionRuns` lists all five in fixed order, and `sections` holds the 3 finished texts in section order. Check: `bun test src/reports.test.ts`.
- [ ] Given every section has reached a terminal state with at least one `failed` and one `done`, then `status` is `partial`. With all `failed` it is `failed`; with all `done` it is `done`. Check: `bun test src/reports.test.ts`.

## Architecture Decisions

| Aspect | Decision |
| --- | --- |
| Layers touched | HTTP handlers (API + worker role), persistence (Firestore), integration (model API client, Cloud Tasks), deploy/infra |
| Domain modules | existing `app`, `db`, `llm`; new `reports` (section list, status derivation), `db-firestore`, `queue`, `spend`, `worker`, `metrics` |
| Data flow | caller → API (validate, auth, cap pre-check) → Firestore report + 5 section rows → 5 Cloud Tasks → private worker → model API → Firestore section text → caller polls `GET` |
| Pattern | new: parent report row + one child section row per step, one queued task per section, status derived from children. The repo has no prior async pattern, so this follows the system-design skill's "multi-section work" row |
| Binary framing | the request reads as "generate in the request". Middle ground considered: one queued task per report that checkpoints each section. Recorded under Decision analysis |
| Goal anchor | every decision is checked against the Goal's "survives restarts, never double-charges, within a daily cap". Inline generation fails all three |

### Runtime design

| Operation | Est. p99 | Execution model | Timeout / deadline | Retries | Idempotency key | Cost bound |
| --- | --- | --- | --- | --- | --- | --- |
| `POST /reports` (create) | ~1.5 s | inline — 1.5 s, timeout 8 s | store write 3 s, each enqueue 2 s | none server-side; caller may retry with `Idempotency-Key` | `Idempotency-Key` header (sha256) → report id; key with a different body → 422 | 0 paid calls in the request; cap pre-check needs ≥ 5 remaining or returns 429 |
| Section generation (5 per report) | ~65 s per attempt | queue: one Cloud Tasks task per section, worker invoked synchronously under the dispatch deadline | dispatch deadline 180 s > worker handler 150 s > model call 90 s; worker service request timeout 240 s | queue layer only: max 4 attempts, backoff 10 s → 300 s, max doublings 4; no in-code retries | task name `<reportId>-<section>` + conditional claim of the section row (lease 200 s) | new single spend ledger: one unit reserved per attempt before the call; daily cap `REPORTS_DAILY_SECTION_CAP` (default 200) |
| Model API call (`generateSection`) | ~60 s | called only inside the worker | 90 s abort signal | none (queue retries) | inherits the section key | counted by the ledger above |

**Platform:** gcp

**Proportionality:** Left out on purpose:

- No workflow engine and no finalize task. Report status is derived on read, and there is no title step to assemble.
- No SSE or WebSocket. Polling is enough for jobs lasting minutes.
- No outbox relay. An enqueue failure after commit marks that section `failed` (`internal`), so the report ends `partial` instead of hanging.
- No per-IP rate limiter. The API key, the daily cap, the queue's `maxDispatchesPerSecond=1` / `maxConcurrentDispatches=10` and the instance caps bound overload.
- No Pub/Sub, canary analysis or multi-region. There are no live users to compare a canary against.

**Recovery:** Firestore is the store for paid generations (each report can be regenerated for 5 model calls) and share flags (user state). Turn on point-in-time recovery (7-day window) and a daily backup schedule with 7-day retention. A restore check restores the latest backup to a scratch database and compares document counts (Task 9). Firestore TTL prunes `idempotency` documents after 24 h.

**Rollback:** Task 10 — `infra/rollback.sh` shifts both services back to their previous revision. Setting `REPORTS_DAILY_SECTION_CAP=0` stops all new paid work without a code change. Queue payloads carry `version: 1` so a rolled-back worker can still read in-flight tasks.

## Technical Constraints

- Section calls take 20–60 s and are paid, so no section call may run in a request handler [src/llm.ts:1].
- Work after the response is throttled under request-based billing, and the request timeout defaults to 300 s (max 60 min), so generation must live in the queue-driven worker, not after a `202` on the API instance [https://docs.cloud.google.com/run/docs/configuring/billing-settings].
- Cloud Tasks HTTP dispatch deadline defaults to 10 min (max 30 min), and named tasks dedupe only for a while, so the consumer must also dedupe [https://docs.cloud.google.com/tasks/docs/creating-http-target-tasks].
- "No new runtime dependencies without a reason": this plan adds exactly two, `@google-cloud/firestore` (durable shared store) and `@google-cloud/tasks` (durable queue). Both are named with that reason in package.json's PR [AGENTS.md].
- The public service is deployed `--allow-unauthenticated`. The worker must be a separate service deployed `--no-allow-unauthenticated`, invocable only by the queue's service account (`roles/run.invoker`) [deploy.sh:3].
- **Cost:** each report costs 5 model calls when nothing fails and at most 20 when every section uses all 4 attempts. The daily cap is the hard ceiling: 200 calls/day by default, about 40 clean reports. The model API's per-call price is not in the repo, so the dollar ceiling is unknown. Firestore and Cloud Tasks at this volume sit within free tiers or cost cents a month (medium confidence).
- **Latency:** a report is ready after the slowest of its five parallel sections, about 1 min typical and several minutes with retries, not on the `POST` response.

## Open Questions

- [ ] Q1. Which five sections make up a company report? Redirecting changes only the `SECTION_NAMES` constant and its test.
  - **Stakes:** user — readers get sections that don't match what they expect from a company report.
  - **Needs user input:** a user-held preference or subjective taste. The request says "five sections" but not which. The plan ships the placeholders `Company overview`, `Products and services`, `Market and competitors`, `Financial performance`, `Risks and outlook`.
- [ ] Is a `202` + poll contract acceptable instead of returning the finished report in the `POST` response? Redirecting to synchronous drops the queue, worker and lease tasks.
  - **Stakes:** user — a caller that expects the report in the response body has to poll `GET /reports/{id}`.
  - **Recommended:** `202` + poll — five calls at 20–60 s cannot fit a 10 s interactive budget, and the sequential worst case meets Cloud Run's 300 s timeout [confidence: high] [anchor: src/llm.ts:1]
- [ ] Should `POST /reports` require an API key (`Authorization: Bearer`, value in Secret Manager)? Redirecting to "open" removes the auth check and leans on the daily cap alone.
  - **Stakes:** both — without a key any internet caller can spend the whole daily cap (cost). With one, existing integrations must send it (user).
  - **Recommended:** require the key on `POST /reports` only and leave `GET`/share as they are [confidence: medium] [anchor: weighing: risk — deploy.sh deploys the service unauthenticated, so an open POST lets anyone trigger paid calls up to the cap]
- [ ] Which durable store: Firestore (serverless) or Cloud SQL Postgres? Redirecting rewrites Tasks 4 and 9.
  - **Stakes:** system — Cloud SQL adds an always-on instance cost and connection pooling. Firestore limits query flexibility.
  - **Recommended:** Firestore in Native mode — no instance to run, scales to zero with Cloud Run, PITR and scheduled backups built in [confidence: medium] [anchor: weighing: footprint — no always-on database instance, no connection pool, one client dependency]
- [ ] What default daily cap? Redirecting changes one env default and the deploy flag.
  - **Stakes:** both — too low returns 429 to legitimate callers. Too high lets a runaway caller spend more before anyone notices.
  - **Recommended:** `REPORTS_DAILY_SECTION_CAP=200` (about 40 clean reports a day), changeable per deploy without a code change. `0` is the kill switch [confidence: medium] [anchor: weighing: reversibility — an env value change, no code change, takes effect on the next revision]
- [ ] Should a report also get a model-suggested title? Redirecting adds a sixth paid call (1–3 s) as a finalize step once all sections are done.
  - **Stakes:** user — reports show `title: null`.
  - **Recommended:** no title call. Keep `title: null` and generate exactly five calls per report [confidence: high] [anchor: user: "calling the model API once for each of five sections"]
- [ ] When some sections fail, show the ones that succeeded (`partial`) or fail the whole report? Redirecting to all-or-nothing hides the successful sections behind `failed`.
  - **Stakes:** user — an all-or-nothing report throws away sections that were already paid for and finished.
  - **Recommended:** `partial`, with failed sections listed in `sectionRuns` [confidence: medium] [anchor: weighing: risk — all-or-nothing discards up to four already-paid sections whenever one fails]
- [ ] Should the worker run as a separate private Cloud Run service, or as a route on the public service that verifies the queue's OIDC token? Redirecting adds a JWT-verification dependency and drops the second deploy.
  - **Stakes:** system — a mis-verified token on a public route lets anyone run paid work while skipping the queue's caps.
  - **Recommended:** a separate service from the same image (`ROLE=worker`, `--no-allow-unauthenticated`, invoker = queue service account) [confidence: medium] [anchor: weighing: footprint — IAM rejects every non-queue caller with no token-verification code or dependency]

## Decision analysis

**Decision A — How do the five section calls run?**

| Branch | End-user flow | System flow | Friction |
| --- | --- | --- | --- |
| A1. Inline in `POST` (literal request) | The caller sends `POST` and waits 1–5 min. On a slow day the request dies at 300 s and the caller retries, paying for all five sections again | 5 paid calls per attempt; no durable state; in-memory store loses the result on restart | 1 blocking wait per run, 60–300 s |
| A2. One queued task per report, checkpointing each section | `POST` returns `202` in < 2 s, then the caller polls | the worker runs 5 calls in parallel and saves each as it finishes. A retry skips saved sections, but one 90 s timeout re-runs the whole task's attempt budget for the rest | 0 blocking waits; caller polls every 1–10 s |
| A3. One queued task per section (chosen) | Same as A2 | each section has its own attempt budget, backoff and lease. The queue's concurrency cap bounds model calls directly. Status is derived on read | 0 blocking waits; caller polls every 1–10 s |

Exclusivity: A1, A2 and A3 are mutually exclusive execution models. The durable store and the spend cap go with A2 or A3 and are required by both.

Ranked combinations: A3 + Firestore + cap > A2 + Firestore + cap > A1 (fails the Goal on restarts, retries and budget).

Verdict: **A3** — per-section tasks retry only the failed section and let the queue cap concurrent model calls, at no extra cost over A2 [confidence: medium] [anchor: weighing: risk — a single per-report task spends one attempt budget on five independent paid calls]

## Alternatives considered

- **Generate all five sections inside the POST request and return the finished report** — rejected: 5 × 20–60 s (src/llm.ts:1) is 100–300 s, over the 10 s interactive budget, and the sequential worst case meets Cloud Run's 300 s default request timeout.
- **Return 202 and keep generating on the same instance with a detached promise, storing results in the in-memory map** — rejected: request-based billing throttles CPU after the response (https://docs.cloud.google.com/run/docs/configuring/billing-settings), and src/db.ts:9's map is lost on restart and invisible to other instances.
- **Hand-rolled REST calls to Firestore and Cloud Tasks via fetch to avoid new dependencies** — rejected: Firestore REST needs hand-written typed-value encoding, begin/commit transactions and token refresh. AGENTS.md allows a dependency with a stated reason.

## Recommendation

**Reconsider scope** — build `POST /reports` as asked, but as accept-then-poll on a queue with a durable store, an API key and a daily cap, rather than generating inside the request. See the `202` + poll and API-key Open Questions. The existing persistence module is rewritten and the model client simplified [confidence: high] [anchor: src/llm.ts:1]

**Redundancy:** none found — no existing route, job or helper creates reports. `generateSection` exists but has no caller (src/llm.ts:2).

## Plan risks

The plan assumes the user wants a production-bound service. The in-memory store and open deploy suggest a prototype, and if so the ten-task Firestore + Cloud Tasks + private-worker build is more than they wanted. Inline generation is still ruled out by the 300 s timeout either way.

## Cut list

- `reports.llm.duration` almost duplicates `reports.section.duration`, since the model call is most of each attempt. Drop it if the reviewer wants fewer series (saves 24 per instance).
- `Idempotency-Key` handling (the `idempotency` collection plus TTL) could be cut if the only caller never retries a `POST`. It stays because a double-submit otherwise costs 5 paid calls.

# PR description draft

## TLDR

Before, the service had no way to create a company report; now `POST /reports` answers within seconds with a link to poll while its five sections fill in.

## User-facing changes

- New endpoint: `POST /reports` with `{"company": "<name>"}` and an API key starts a five-section report and returns `202` with a link to it.
- Re-sending a request with the same `Idempotency-Key` returns the same report and is not charged again. The same key with a different body is rejected.
- Requests past the day's spend cap get `429` with a `Retry-After` time and cost nothing.
- Reading a report now shows its progress:
  - **Before:** a report read returned only the stored fields, and no report could ever exist.
  - **After:** a report read also returns an overall status (`queued`, `running`, `partial`, `failed`, `done`) and each section's progress. Finished sections appear as they complete.
- Reports now survive deploys and restarts:
  - **Before:** reports lived in one server's memory and vanished on every deploy.
  - **After:** reports are kept in a managed database with daily backups and 7-day point-in-time recovery.

## System changes

- Generation is now queued:
  - **Before:** the model client had no caller, no timeout and no error handling.
  - **After:** each section is one queued task on a private worker service. Each model call has a 90 s timeout, retries happen only in the queue (up to 4 attempts), and a section that keeps failing ends in a visible `failed` state.
- The service is now two services: a public API, and a private worker that only the queue can call.
- New ongoing cost: 5 paid model calls per report when nothing fails, at most 20 with retries, capped at 200 calls a day by default. The database and queue cost cents a month at this volume (medium confidence). Two runtime dependencies are added: the official Firestore and Cloud Tasks clients.

## Why

Nothing could create a company report, so the service's read and share features had nothing to serve. Each section takes up to a minute of paid model time. Waiting on five of them in one request makes callers wait minutes, risks the platform cutting the request off, and lets a retry or an anonymous caller run up the model bill.

## Key decisions

- Accept-then-poll instead of returning the report in the response: five calls of 20–60 s cannot fit a usable request, and the sequential worst case meets the platform's 5-minute limit.
- One queued task per section rather than one per report, so a failed section retries alone and the queue caps concurrent model calls.
- A serverless managed database (Firestore) over a SQL instance: no always-on instance cost and built-in recovery.
- An API key on report creation only. Reading and sharing stay as they are, and an ownership model is out of scope.
- One daily cap on section calls, checked right before every paid call. Setting it to 0 is the kill switch.
- No title generation, which would be a sixth paid call. Reports keep an empty title.
- Partially failed reports show the sections that succeeded instead of failing the whole report.
- Bundled: the missing timeout and unchecked HTTP status in the existing model client.
- Bundled: replacing the in-memory store, a prerequisite for the API and the worker to share reports.

## Instrumentation

These metrics are recorded through a new in-memory metrics helper but will not show on any graph until a metrics backend is chosen. The suggested backend is Google Cloud Monitoring via OTLP, and its status is tracked in the new metrics contract file. Spec-only: there is no dashboard URL yet.

- Report creation: duration by outcome, failures by type (budget exhausted, internal, invalid input, unauthorized).
- Section generation: per-attempt duration by outcome, failures by type (budget exhausted, internal, rate limited, upstream error, upstream timeout), and model-call duration.
- Panels on a new "reports-service overview" dashboard: create rate and failures, section success vs failure with p50/p95/p99, model-call p95/p99, queue depth.
- Alerts (notify): queue depth over 50 for 15 minutes, and any budget-exhausted section within 5 minutes. Plus burn-rate tiers on the new "generate a company report" SLO (98% of section attempts succeed over 30 days).
