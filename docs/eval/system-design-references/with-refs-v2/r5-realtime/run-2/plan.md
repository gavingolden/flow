# PRD

# Live section-by-section report progress

**Goal:** A reader watching a report sees each finished section appear on its own within about three seconds, and the page stops checking once the report is complete.

## Problem Statement

A report is written one section at a time, and each section takes between twenty seconds and a minute to produce. Today the only way to see a new section is to reload the page, so readers sit refreshing, guessing whether anything has changed. That costs them attention and patience on every report, and it tells them nothing about how much is left.

Evidence from the codebase:

| Fact | Anchor |
| --- | --- |
| Each section is generated by its own queued task, so sections finish independently and in no fixed order | [anchor: src/queue.ts:1] |
| One section's model call takes 20–60 s and costs money per call | [anchor: src/llm.ts:1] |
| The report read already returns every section, with unwritten ones as an empty body | [anchor: src/app.ts:14] [anchor: src/db.ts:12] |
| Nothing in the read tells a page how many sections are left or when to stop checking | [anchor: src/app.ts:14] |
| The worker's server uses the runtime's default 10 s idle limit; reproduced locally on Bun 1.3.11, a handler slower than 10 s has its connection closed (`bun s.ts` → `[Bun.serve]: request timed out after 10 seconds`) | [anchor: src/app.ts:19] |
| A redelivered section task pays for a fresh model call and overwrites the text already shown | [anchor: src/worker.ts:9] [anchor: src/db.ts:16] |

The page itself is not in this repository: the container ships only the service code and serves no HTML [anchor: Dockerfile:4]. This plan delivers the service half — a report read that a page can check cheaply every few seconds and knows when to stop — plus the worker fixes without which sections may not arrive reliably.

**Research findings (prior context).** Web-grounded gather ran; both adversarial refute passes failed to run (agy error), so nothing below was independently checked.

- (high — matches the system-design platform reference) Cloud Run kills a request at the service timeout, 300 s by default, 3600 s maximum; a stream must reconnect.
- (medium) Under request-based billing an instance is billed in full while at least one request is open; one idle push stream bills its instance for the whole time it is open.
- (medium) Each open stream holds one of the instance's concurrent-request slots (default 80) for its lifetime.
- (medium) Bun closes a quiet stream after 10 s unless it sends a heartbeat or raises the idle limit — consistent with the local reproduction above.
- (low — single unverified source) Bun's built-in Postgres client gained LISTEN/NOTIFY only in a late 1.x release. Treated as a risk against the notify-based option, not a fact.

## Request vetting

- **Hypothesis:** Because each section takes 20–60 s, a page that re-checks the report every 3 s shows every finished section within ~3 s — indistinguishable in practice from a push stream — while costing a short request per check instead of an open, billed connection.
- **Case against:** The user said "live", which may mean watching text appear as it is written; section-level updates leave 20–60 s gaps where nothing moves [anchor: src/llm.ts:1]. Each check also re-reads and re-sends every finished section's full text [anchor: src/app.ts:14], so naive polling multiplies egress by watchers × checks unless unchanged checks get an empty reply. MDN recommends Server-Sent Events for server-to-client event streams: https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events
- **Sources:** https://cloud.google.com/run/docs/configuring/cpu-allocation ; https://cloud.google.com/run/docs/configuring/request-timeout (research gather, refute pass did not run)
- **Verdict:** adopt-with-conditions: the report read answers an unchanged check with an empty 304 reply and reports sections done out of total, so a page checking every 3 s can stop when the report completes

## Scope Boundary

**In scope:**

- The report read returns a `progress` count (sections done, total) and answers unchanged checks with an empty 304.
- The worker's server keeps slow section requests open past the 10 s default.
- The model call gets an explicit timeout and rejects error replies instead of saving them as text.
- A redelivered section task skips the paid model call when the section is already written, and never overwrites it.
- First-time metrics contract and helper for the operations above.
- The section queue gets an explicit retry cap (5 attempts) and each section task an explicit 300 s dispatch deadline, so a failing paid call cannot repeat under the platform default policy.

**Out of scope:**

- Changing the page itself — it lives outside this repository; the polling contract ships in the PR description.
- Token-by-token streaming of a section's text (see Alternatives considered).
- A push stream (Server-Sent Events) — the open fork in Decision analysis; not built.
- A "failed" state for sections that the page can show (candidate follow-up).
- Locking down the worker endpoint to the queue's identity (candidate follow-up).

## Behavioral contrast

### User flow

| Before | After (once the page adopts the 3 s check) |
| --- | --- |
| Reader reloads the page to find out whether a new section exists | Each finished section appears within ~3 s with no reload |
| Reader cannot tell how much of the report is left | Page can show "3 of 7 sections written" |
| A section's text can silently change after it was shown, when its task is redelivered | A section's text never changes once shown |

### System flow

- **Before:**
  - Every read returns the full report body, whether or not anything changed.
  - The worker's server closes any request idle for more than 10 s, while a section's model call takes 20–60 s.
  - The model call has no timeout and saves whatever the reply contains.
  - A redelivered section task calls the model again and overwrites the saved text.
  - The section queue carries no retry settings, so the platform default policy decides how often a failing paid call repeats.
- **After:**
  - A read carries a version tag; a check that sends the last tag back gets an empty 304 when nothing changed.
  - The worker's server allows 120 s idle; the model call is cut at 90 s; both sit inside a 300 s per-task dispatch deadline.
  - An error reply from the model fails the task (so the queue retries) instead of being saved.
  - A section task is attempted at most 5 times, with 10–300 s backoff.
  - A redelivered task for an already-written section returns success without calling the model.

**Lost:** a re-run of a section's task no longer replaces its text — deliberately regenerating a section would need a separate path.

- [ ] Given a worker request that takes 11 s, when it is served, then the caller receives 200 rather than a closed connection — `bun test src/server.test.ts` passes.
- [ ] Given a model reply that is not a success, when a section is generated, then an error is raised and nothing is saved — `bun test src/llm.test.ts` passes.

## Architecture Decisions

| Aspect | Decision |
| --- | --- |
| Layers touched | HTTP handlers, worker, model-API client, persistence (query only, no schema change) |
| Domain modules | existing `src/app.ts`, `src/worker.ts`, `src/llm.ts`, `src/db.ts`; new `src/metrics.ts` |
| Data flow | worker writes a section → stored body → page re-reads the report every 3 s → 304 when unchanged, 200 with new sections and progress otherwise |
| Pattern | existing: the stored row is the source of truth and the page polls the status resource (system-design realtime guidance: polling suffices for work taking tens of seconds) |
| Binary-framing check | not framed as a binary; the fork polling vs push stream vs notify-backed stream is simulated in Decision analysis, with "poll now, stream later only if token streaming lands" as the middle option |

### Runtime design

| Operation | Est. p99 | Execution model | Timeout / deadline | Retries | Idempotency key | Cost bound |
| --- | --- | --- | --- | --- | --- | --- |
| Report read (page check) | ~100 ms | inline — ~100 ms, timeout 300 s (Cloud Run default, unchanged) | 300 s | none server-side; the page simply checks again | n/a — read only | unchanged check answers 304 with no body; one small query per check |
| Section worker | ~60 s | existing Cloud Tasks queue; worker runs synchronously under the task's dispatch deadline | dispatch deadline 300 s (new, per task) > server idle limit 120 s | queue layer only: max 5 attempts, backoff 10–300 s (new); no retry in the worker | business identity (report id, section name): skip when the section is already written; first write wins | no spend ledger exists; redelivery skip removes repeat paid calls |
| Model call | ~60 s | inline inside the worker | 90 s abort | none at this layer — the queue retries | n/a — guarded by the worker's key | one paid call per section per successful first delivery |

**Platform:** gcp

**Proportionality:** No push stream, no notify listener, no new table or queue: sections take 20–60 s, so a 3 s check adds at most ~3 s of delay. No spend ledger in this change — the 5-attempt cap bounds spend at 5 paid calls per section, and the redelivery skip removes repeat calls after success; a repo-wide ledger is not needed for one paid call site. No failed-section state (candidate follow-up).

**Recovery:** none — no table, migration or bucket is added or changed; only queries change.

## Technical Constraints

- The worker's server must keep a request open longer than the slowest model call: Bun's default 10 s idle limit closes a slower handler (reproduced locally on Bun 1.3.11) and the model call takes 20–60 s [anchor: src/llm.ts:1] [anchor: src/app.ts:19]. Idle limit 120 s (Bun's maximum is 255 s), model abort 90 s.
- Deadlines shrink inward: per-task dispatch deadline 300 s (the default is 10 minutes, maximum 30, per the system-design GCP reference) > server idle 120 s > model abort 90 s; the Cloud Run request timeout (300 s default) also bounds the worker request.
- The queue already exists in production and `deploy.sh` swallows the create failure (`|| true`) [anchor: deploy.sh:3], so retry settings must be applied with an update, not only on create.
- No new runtime dependencies (AGENTS.md); the version tag uses the built-in `Bun.hash`, and the metrics helper is an in-memory recorder.
- The report read stays as open as it is today (`--allow-unauthenticated`, no auth check) [anchor: deploy.sh:4]; this change adds no new exposure but does not fix it.
- Latency/cost: each watching page adds one ~100 ms request every 3 s while a report is unfinished; unchanged checks carry no body.

## Open Questions

- [ ] The page users refresh is not in this repository — this plan ships only the service half plus a written polling contract. On redirect (the page is here after all), a UI task is added.
  - **Stakes:** user — if wrong, readers see no change until someone wires the page; this lands on user experience, the brief's top priority.
  - **Recommended:** service half here; the page's owner adds the 3 s check using the contract in the PR description — the container ships only service code and no route serves HTML [confidence: high] [anchor: Dockerfile:4]
- [ ] "Live" means section by section, not text appearing word by word. On redirect, the plan becomes token streaming: a streaming model call, partial text persistence and a push stream.
  - **Stakes:** user — if readers expected to watch text being typed, a 20–60 s gap between updates feels stuck; user experience, the brief's top priority.
  - **Recommended:** section granularity — the request says so verbatim [confidence: high] [anchor: user: "section by section"]
- [ ] The page checks every 3 s rather than holding a push stream open. On redirect, a stream endpoint with heartbeats replaces the conditional read (Decision analysis).
  - **Stakes:** both — user experience (delay of up to ~3 s) versus cost (an open stream bills its instance the whole time it is open); the brief ranks user experience over cost, and with 20–60 s sections the 3 s delay is not noticeable, so cost decides.
  - **Recommended:** 3 s polling with 304 replies [confidence: medium] [anchor: weighing: footprint — a 3-minute watch is ~60 short requests instead of one connection holding a billed instance for 180 s, with the same ~3 s worst-case delay as a stream that re-checks the database]
- [ ] Progress is counted at read time from written sections; the stored report status is left as is. On redirect, the worker also marks the report complete.
  - **Stakes:** system — if another consumer relies on the stored status, it keeps showing "queued"; that is today's behavior, unchanged.
  - **Recommended:** count at read time — the report rows are created outside this repo, so writing their status here risks clashing with that owner [confidence: medium] [anchor: weighing: reversibility — a read-time count changes no stored data]
- [ ] A section task is capped at 5 attempts. On redirect, the cap value in the queue settings changes.
  - **Stakes:** both — too low drops sections that would have succeeded (readers see an unfinished report); too high repeats paid calls (cost, the brief's second priority).
  - **Recommended:** 5 attempts with 10–300 s backoff — with the idle cut and model timeout fixed, a section that fails 5 times over ~10 minutes is not transient, and 5 bounds spend at 5 paid calls per section [confidence: medium] [anchor: weighing: risk — bounded spend versus the rare transient failure that lasts longer than ~10 minutes]
- [ ] A section whose task gives up stays unwritten forever, so the page cannot tell "failed" from "slow". On redirect, a failed state joins this plan.
  - **Stakes:** user — a reader could watch a report that will never finish; the contract tells the page to stop after 10 minutes and say it is taking longer than expected.
  - **Recommended:** keep it out of this plan; it is the ticked candidate follow-up, because it needs a schema change and a display decision [confidence: medium] [anchor: weighing: footprint — a failed state needs a new column, a migration and a worker branch keyed on the last attempt, roughly doubling this diff]
- [ ] The worker's idle limit is raised server-wide to 120 s rather than only for the worker route. On redirect, the limit is applied per request on the worker route.
  - **Stakes:** system — idle keep-alive connections may linger up to 120 s; negligible at this service's size.
  - **Recommended:** server-wide setting — one option on the existing server start, no per-route branching [confidence: medium] [anchor: weighing: footprint — one option versus a per-request call inside the router]

## Decision analysis

**Decision 1 — How does the page learn that a section finished?**

| Branch | What the reader sees | What they wait for | Interruptions per run | Server cost |
| --- | --- | --- | --- | --- |
| A. Page checks every 3 s; server answers 304 when unchanged | Opens report → sections appear within ~3 s each → counter "4 of 7" → checking stops at 7 of 7 | ≤3 s after a section is saved | 0 — fully automated | one ~100 ms request per 3 s per watcher; unchanged replies have no body |
| B. Push stream (Server-Sent Events), server re-checks the database every 2 s | Same as A, with ≤2 s delay | ≤2 s after a section is saved | 0 — fully automated | one open request per watcher, billing its instance the whole time; heartbeat every <10 s or Bun drops it; reconnect at the 300 s timeout |
| C. Push stream fed by Postgres notifications | Same as B, near-instant | <1 s | 0 — fully automated | as B, plus a dedicated listening connection per instance; the worker must send a notification; Bun's client support is unverified (low-confidence research) |

- **Exclusivity:** A, B and C are mutually exclusive as the primary channel. A's progress count is complementary to B and C — a later stream would reuse it.
- **Ranked combinations:** (1) A alone; (2) A now, B later only if word-by-word streaming is ever built; (3) B alone; (4) C.
- Verdict: **A — poll every 3 s with 304 replies** — with 20–60 s per section, B's and C's lower delay is not visible to a reader, while their open connections cost more and add heartbeat, timeout-reconnect and listener failure modes [confidence: medium] [anchor: weighing: footprint — same reader-visible result, a fraction of the billed instance time]

## Alternatives considered

- **Word-by-word streaming of each section** — rejected: the user asked for "section by section", and it would require a streaming model call in src/llm.ts:6 plus persisting partial text from every worker.
- **WebSockets** — rejected: traffic is strictly server-to-page; the system-design realtime guidance reserves WebSockets for two-way interaction, and Cloud Run caps them at the same request timeout.

## Recommendation

**Reconsider scope** — deliver "live" as a 3 s check against a cheap, terminable report read rather than a push stream, and bundle the worker fixes (idle cut, model-call timeout, overwrite on redelivery, retry cap) without which sections may not arrive; the model client and section save are simplified in place; see the polling-vs-stream Open Question [confidence: medium] [anchor: weighing: footprint — same reader-visible delay as a database-backed stream at a fraction of the billed time]

**Redundancy:** the existing report read (`GET /reports/:id`) already returns finished sections and empty bodies for unwritten ones, so a page could poll it today; this plan makes that check cheap and terminable instead of adding a second channel.

## Plan risks

The page lives outside this repository, so readers see nothing new until its owner adds the 3 s check — the service half alone ships no visible change.

## Cut list

- nothing — plan is minimal: every task is the feature's read path, a worker fix the feature depends on, or the first-time metrics contract; a per-section status field, a push stream and a schema change were already cut.

# PR description draft

## TLDR

A page can now follow a report as it is written — each finished section shows up within seconds and the page knows when to stop — where before readers had to keep reloading.

## User-facing changes

- Reading a report now tells you how many sections are written out of the total.
- Checking a report again when nothing changed now gets an empty "not modified" reply instead of the whole report.
- A section's text no longer changes after it was shown:
  - **Before:** a repeated section job could replace text a reader had already seen.
  - **After:** the first saved text for a section is kept.
- Polling contract for the page (lives outside this repo): check the report every 3 s while written is less than total, send back the last version tag, stop at written == total, and after 10 minutes stop and say the report is taking longer than expected.

## System changes

- Slow section jobs are no longer cut off:
  - **Before:** the server closed any request idle for more than 10 s, while a section's model call takes 20–60 s.
  - **After:** the server allows 120 s, the model call is cut at 90 s, both inside a 300 s per-job deadline.
- Model errors no longer become section text:
  - **Before:** the model call had no timeout and saved whatever the reply contained.
  - **After:** an error or timeout fails the job so the queue retries it.
- Failing section jobs now stop retrying:
  - **Before:** the queue had no retry settings, so the platform default decided how often a failing paid call repeated.
  - **After:** a section job is attempted at most 5 times, 10 s to 5 minutes apart.
- Repeated section jobs no longer pay twice:
  - **Before:** a redelivered job called the paid model again and overwrote the section.
  - **After:** a redelivered job for an already-written section returns success without calling the model.
- Cost: each watching page adds one ~100 ms request every 3 s while a report is unfinished; unchanged checks carry no body. Repeat model calls after a success drop to zero, and a failing section costs at most 5 paid calls.

## Why

Sections take 20–60 seconds each and finish independently, but readers can only see new ones by reloading, with no sense of how much is left.

## Key decisions

- Checking every 3 s instead of a push stream: with 20–60 s per section the extra delay is invisible, while an open stream bills its instance for the whole time it is open and needs heartbeats and reconnects.
- Section-level updates, not word-by-word: the request said "section by section".
- Progress is counted at read time; the stored report status is left alone because reports are created outside this repo.
- Bundled: the 10 s idle cut on slow worker requests, reproduced locally.
- Bundled: a 90 s timeout and error check on the model call.
- Bundled: first-write-wins section saves and a skip for already-written sections.
- Bundled: a 5-attempt retry cap on the section queue and a 300 s per-job deadline, applied on every deploy because the queue already exists.
- Out of scope: a failed state for sections, and locking the worker route to the queue — both filed as follow-ups.

## Instrumentation

spec-only — this PR creates the metrics contract with backend `none yet` (suggested: Google Cloud Monitoring), so these graphs need a backend choice before anything shows. Panels added to "reports-service overview": report-read latency by status class, share of not-modified replies, section-generation latency and failures by type, model-call latency, queue depth. Two new SLOs: report reads 99.5% non-5xx, section delivery 99% ok, both over 28 days; alerts are burn-rate tiers only.
