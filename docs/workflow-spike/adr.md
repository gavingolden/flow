# ADR — workflow-port go/no-go verdict (f5-workflow-spike)

## Context

The steps-5–10 port (`f6-workflow-port`, design.md D5) rests on four capabilities the Claude Code dynamic-workflow runtime does not document. Design.md's verified-premise #1 (2026-08-19) confirmed workflows are GA (`code.claude.com/docs/en/workflows.md`, v2.1.154+) but left helper invocation, plugin-qualified agent spawns with frontmatter pins, hand-back at a human gate, and resume against `~/.flow/state/<slug>.json` unverified. This ADR mirrors the repo's `p6-distribution-eval` precedent (`docs/target-architecture.md`, "ADR — distribution end-state verdict"): a throwaway spike settles the residue empirically before the port is committed.

**Evidence base.** `workflows.md` re-fetched 2026-08-24; local Claude Code build **2.1.243**; four live `Workflow`-tool runs from the `f5-workflow-spike` pipeline's own supervisor session on 2026-08-25 (01:16–01:19 UTC), scripts at [probe-capabilities.workflow.js](./probe-capabilities.workflow.js), [probe-resume.workflow.js](./probe-resume.workflow.js), [probe-invalid-agent.workflow.js](./probe-invalid-agent.workflow.js), runbook at [README.md](./README.md), raw captures under `evidence/`. Two documented narrowings were recorded before any run and are quoted verbatim where they bear on a row: "No direct filesystem or shell access from the workflow itself — Agents read, write, and run commands. The script coordinates the agents" and "No mid-run user input — Only agent permission prompts can pause a run. For sign-off between stages, run each stage as its own workflow", plus "Resume works within the same Claude Code session. If you exit Claude Code while a workflow is running, the next session starts the workflow fresh." `CLAUDE_CODE_SUBAGENT_MODEL` (which overrides every frontmatter model pin) was confirmed unset (`evidence/env-precheck.txt`). Nothing from the spike ships: `flow install` materializes `bin/`, `skills/`, and `agents/`; `docs/` is never scanned.

## Pre-registered rubric

Fixed in the plan before the spike ran:

- **go** ⇔ (1) confirmed on the agent-mediated bar (the row records BOTH sub-verdicts: script-direct per documentation, agent-mediated per observation — never collapsed), (2a) plugin-qualified resolution confirmed AND the `model: haiku` pin observed in a transcript (effort `unobservable` tolerated only with the explicit per-call `effort:` mitigation contracted for f6), (2b) `tools:` allowlist confirmed, (3) confirmed, (4a) confirmed AND the (4b) state.json-skip fallback confirmed.
- **no-go** ⇔ any of: the plugin-qualified `agentType` fails to resolve or the haiku pin is observably not honored; the `tools:` allowlist is observably ignored; the workflow cannot return a verdict without a side effect or cannot be stopped; same-session resume loses completed-agent results AND the state.json skip fails.
- Anything else (e.g. a permission prompt pausing a run) is a run-procedure issue, not a capability verdict.

## Decision

**Decision.** Verdict: **go** — every rubric condition for `go` is met with live, quoted evidence, and no `no-go` trigger fired: plugin-qualified resolution, the `model: haiku` pin, the `effort: low` pin, and the `tools:` allowlist were all observed in transcripts (effort turned out to be observable, so the tolerated-open-assumption clause was not needed); the workflow returned a `stop` verdict with no side effect and was stopped mid-run by `TaskStop`; same-session resume served completed agents from cache; and the state.json-keyed skip worked with no cache at all. `f6-workflow-port` proceeds under the contracted scope below. Had any row been refuted, the fallback would have been to retain the prose state machine (`skills/pipeline/flow-pipeline/SKILL.md`) for steps 5–10 and cancel f6 at the epic-run checkpoint; that fallback still applies to any step f6 cannot port under the constraints below.

## Rejected by name

- **Script-direct helper invocation as the capability bar** — refuted by documentation before any run; judging (1) on it would have decided the epic's biggest question on a definition rather than on the mechanism f6 would use (plan Decision A).
- **Probing cross-session `resumeFromRunId` from a nested `claude` session** — documented same-session only; a nested session inherits `FLOW_SLUG`/`TMUX_PANE` and trips `flow-stop-guard` against the live pipeline (flow#618). Recorded as a candidate follow-up, not asserted either way.
- **Shipping the spike as a `MAINTAINER_ONLY` `bin/*.ts` helper** — the manifest forbids install-surface changes and the Workflow script is harness-executed JavaScript, not a Bun CLI.
- **A tenth Task-tool exemption for the spike's `Workflow` calls** — a one-time, user-instructed, throwaway exception recorded here only; the ledger changes shape in f6, not before.

## Contracted scope for f6-workflow-port

1. **Helper calls are thin agent steps, not script code.** Every `flow-*` helper the ported steps invoke runs inside a schema-typed `agent()` that returns the helper's JSON verbatim; the port's helper count maps to agent count, at roughly 30–40k subagent tokens and 5–15 s per trivial call (measured above). Batch adjacent helper calls into one agent where ordering allows.
2. **Every mechanical `agent()` passes `model:` and `effort:` explicitly** (both documented `agent()` options) even though frontmatter pins were observed honored — the pins are one `CLAUDE_CODE_SUBAGENT_MODEL` away from being overridden, and explicit options make cost routing auditable in the script.
3. **One workflow per inter-gate stage.** The runtime has no mid-run user input; the workflow returns a verdict object (`stop` / `would-auto-merge` / a failure class) and the supervisor's prose gate (step 9's `flow-gate-decide` + `flow-merge-guard`) stays the only merge authority. Steps 9–10 are not ported.
4. **Every ported step is idempotent against `~/.flow/state/<slug>.json`.** The first agent of each stage reads `phaseLog`/`pr`/`ciWait` and the script skips what is already done; `resumeFromRunId` is used only for same-session relaunches. `flow feature resume` relaunches the stage fresh.
5. **Helper calls carry the slug explicitly** (`FLOW_SLUG=<slug> <helper> --slug <slug>`); workflow agents inherit the session environment, so ambient-slug resolution is not a safety net.
6. **Agents run in `acceptEdits` and inherit the session allowlist**; the port's agent prompts must stay within already-allowlisted commands or the run pauses on a permission prompt.
7. **Transcripts are evidence.** Per-agent `.jsonl` + `.meta.json` under `<session>/subagents/workflows/<runId>/` record `model`, `effort`, `agentType`, and tool use; f1's eval harness can grep them.

## Open assumptions

- **Cross-session `resumeFromRunId`** is unverified (documented unsupported); the state.json skip is the anchor the port relies on. A future probe needs a `FLOW_SLUG`-stripped throwaway session launch shape (candidate follow-up, flow#618).
- **Permission-prompt behaviour under non-auto modes** was not exercised: this session launched all four runs without a consent prompt. A `manual`/`acceptEdits` session prompts per run unless "don't ask again" was recorded.
- **Per-agent token cost** was measured on trivial prompts; real helper steps carry larger prompts and outputs.
- **Runtime drift.** All observations are pinned to Claude Code 2.1.243 on 2026-08-25; re-run the three scripts per the runbook before f6 lands on a newer build.
- **Post-evidence hardening.** `probe-resume`'s Phase B timeout path was hardened after the evidence runs; the committed evidence predates that edit and is unaffected because the marker was released well inside the 540 s cap (`ci-wait` logged at 01:18:25Z, seconds after the interrupt/resume relaunch).
