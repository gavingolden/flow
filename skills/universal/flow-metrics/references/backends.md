# Backend mapping

How `flow-metrics` names and records the same signals on Prometheus, Datadog, Google Cloud Monitoring and Cloudflare Workers Analytics Engine, how to detect which one a repo uses, and the adapter and test recipe the repo-local helper wraps. Facts marked medium confidence (some limits, prices and package names): verify them against the live page before relying on them.

Sources: https://prometheus.io/docs/practices/naming/ (units, `_total`, label cardinality); https://docs.datadoghq.com/account_management/billing/custom_metrics/ (custom metric counting); https://developers.cloudflare.com/analytics/analytics-engine/platform/limits/ (limits); https://opentelemetry.io/docs/specs/otel/compatibility/prometheus_and_openmetrics/ (dotted attribute names to labels); https://docs.datadoghq.com/getting_started/tagging/ (tag syntax); https://docs.cloud.google.com/stackdriver/docs/reference/telemetry/v1.metrics (Cloud Monitoring metric kinds and names).

Prefer Prometheus histograms over summaries: histogram buckets aggregate across instances and summary quantiles do not. The default (classic) OpenTelemetry-to-Prometheus translation renders `http.server.request.duration` as `http_server_request_duration_seconds` and replaces the dots in attribute keys with underscores; Prometheus 3 UTF-8 names can keep dots under some translation strategies, so never register two keys that differ only by `.` versus `_`.

## Datadog

- A distribution gives global percentiles. Datadog bills one custom metric per unique name plus tag-value combination, so an unbounded tag multiplies the bill the same way an unbounded label multiplies Prometheus series.
- Percentile aggregations on a distribution add billed series per combination. The multiplier (five series per combination, more with percentiles) is medium confidence: verify against the live billing page.

## Google Cloud Monitoring

Two ingestion routes, with different billing. OTLP or Managed Prometheus (`prometheus.googleapis.com`): billed per sample, no free allotment. Default new repos to OTLP. The Node Cloud Monitoring exporter (`@google-cloud/opentelemetry-cloud-monitoring-exporter`) is deprecated by Google and its default metric prefix is `workload.googleapis.com`, not `custom.googleapis.com` (https://github.com/GoogleCloudPlatform/opentelemetry-operations-js); keep it as a detected legacy route, read the actual prefix from its config, and migrate dashboards and alerts when moving to OTLP. `flow-metrics` step 9 records the route in `## Backend`.

- Cost (OTLP and Managed Prometheus route): metrics are $0.06 per million samples for the first tier; a scalar point is 1 sample, an explicit-bucket distribution point is 2 plus 1 per non-zero bucket. Legacy exporter metrics bill per MiB: about (scalar points x 8 + distribution points x 80) / 1,048,576 MiB a month, 150 MiB free (medium confidence). All pricing is medium confidence: verify against https://cloud.google.com/products/observability/pricing.
- State samples per month = sum over series of samples per point x (2,592,000 / export interval in seconds) x reporting instances. For the conventions example at a 60 s interval: (2 outcome series x up to 17 samples + 11 counter series x 1) x 43,200 is about 1.94 million samples, about $0.12 a month per operation per instance. A 10 s interval costs 6 times as much. A gauge sampled every 60 s is 43,200 samples a month. Pin the adapter's export interval at 60 s or longer (`exportIntervalMillis: 60000`), since cost scales with it.
- Limits: 30 labels per custom metric descriptor (200 for Prometheus metrics), 200,000 active series per monitored resource for custom metrics (1,000,000 for Prometheus), one point per series per write, points at least 5 s apart. Google advises against IDs, timestamps and raw URLs as labels (https://docs.cloud.google.com/monitoring/quotas, https://docs.cloud.google.com/monitoring/custom-metrics).
- Dotted keys: Google's direct OTLP (Telemetry API) path keeps dots in label keys (https://cloud.google.com/blog/products/management-tools/otlp-opentelemetry-protocol-for-google-cloud-monitoring-metrics), while Managed Prometheus and the Collector `googlecloud` exporter turn them into underscores. Dashboard queries and alert conditions use the stored form for the recorded route.
- Dashboards and alerts as code: Monitoring API JSON, or Terraform `google_monitoring_dashboard` and `google_monitoring_alert_policy`. Set the dashboard's `name` to `projects/<project>/dashboards/<fixed-id>` so its ID, and so its URL, never changes (https://docs.cloud.google.com/monitoring/dashboards/api-dashboard). Record the console URL once in `.flow/metrics.md` `## Dashboards`, and never recreate a dashboard to change it.
- Access: viewing the graphs needs `roles/monitoring.viewer` (or equivalent metric-read permissions) on the project; Dashboard Configuration Viewer (`roles/monitoring.dashboardViewer`) reads only the dashboard configuration, not the metric data. A shared dashboard URL still needs the viewer role, so links stay behind IAM (https://docs.cloud.google.com/monitoring/access-control).
- Alerting: alert policies route through notification channels (email, Slack, mobile push, PagerDuty, webhooks), and the policy's `documentation.links` (up to 3) carries the dashboard link.

## Cloudflare Workers Analytics Engine

- Limits: at most 20 blobs, 20 doubles and 1 index per data point, and at most 250 data points per Worker invocation. Counts are high confidence; individual blob and index byte sizes are medium confidence: verify against the live limits page.
- Sampling is equitable per index, so every query must weight by the sample interval: use `SUM(_sample_interval)` for counts, never `COUNT(*)`, and `quantileWeighted(0.95)(double1, _sample_interval)` for percentiles.
- There is no in-memory exporter. Quantiles are computed in SQL at query time, not at write time.
- Slots: each key owns a fixed `blobN` or `doubleN` slot, recorded in the `slot` column of `.flow/metrics.md` `## Attributes`. New keys only append to the next free slot; never reorder or reuse one, because shifting positions breaks queries over stored data points.
- Tenant as the index: Cloudflare documents the index as the sampling key, with a customer ID as the example, and allows one per data point. A dataset indexed by tenant moves `op` into a blob. Decide the index when the dataset is created, never by re-slotting an existing one.
- Queue backlog and age come from Cloudflare Queues' own metrics. The custom-gauge fallback is one line: sample only an externally readable level (a queue or database read) from a Cron Trigger (`scheduled` handler), never from a queue consumer's batch callback, which goes silent exactly when the consumer stalls. An in-flight or pool count lives in the worker's isolate, so a Cron Trigger would report zero while workers are busy: use a platform-native metric or an explicit shared-state source for those. Read the peak with an unweighted `MAX`, because a maximum cannot be weighted.

## Detection signals

Check the dependency manifest and config files in this order and stop at the first match; record the result in `.flow/metrics.md` `## Backend`.

| Backend                  | Signals                                                                                                                                                                                                           |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Google Cloud Monitoring  | `@google-cloud/opentelemetry-cloud-monitoring-exporter` (medium confidence), a `googlemanagedprometheus` or `googlecloud` exporter in an OpenTelemetry Collector config, `google_monitoring_` resources in `*.tf` |
| OpenTelemetry            | `@opentelemetry/api`, `@opentelemetry/sdk-metrics`, `opentelemetry-sdk`, `go.opentelemetry.io/otel`                                                                                                               |
| Prometheus               | `prom-client`, `prometheus_client`, `github.com/prometheus/client_golang`, a `/metrics` route                                                                                                                     |
| Datadog                  | `dd-trace`, `hot-shots`, `datadog-metrics`, `datadog` in Python requirements, a `statsd` client                                                                                                                   |
| Workers Analytics Engine | an `analytics_engine_datasets` block in `wrangler.toml` or `wrangler.jsonc`                                                                                                                                       |
| none yet                 | none of the above: record `none yet — suggested: <x>`                                                                                                                                                             |

A repo runs on GCP when it has `cloudbuild.yaml`, an App Engine `app.yaml`, a Cloud Run service YAML or a Terraform `google` provider. When no backend is found, the suggested default is Workers Analytics Engine on Cloudflare, Google Cloud Monitoring on GCP, and the OpenTelemetry SDK elsewhere. Do not install or configure it.

Platform-native saturation signals are free of custom code: Cloudflare Queues analytics, OpenTelemetry `http.server.active_requests` and `db.client.connection.*`. Auto-instrumentation signals (do not hand-write the metrics these emit): an OpenTelemetry SDK or Java agent in the start command or dependencies (https://opentelemetry.io/docs/zero-code/java/agent/), framework instrumentation packages (`@opentelemetry/instrumentation-*`), and `dd-trace` auto-init. They emit the HTTP-edge duration histogram with `error.type`; custom metrics go where they are blind: stages, outbound calls, jobs and domain failures behind a 200 response.

## Adapter shape

The helper owns one `Recorder` interface (`observe(name, seconds, attrs)`, `increment(name, attrs)`) and one adapter per backend. Handlers never touch an adapter. When the repo first emits a custom gauge or up-down counter, the `Recorder` also gains `set(name, value, attrs)` and `add(name, delta, attrs)`; they are not starter boilerplate.

The helper binds the allowed keys per instrument, so a disallowed key fails the repo's typecheck: the keys per instrument are exactly those in the conventions instruments table (the source of truth), plus registry keys marked `any`; each custom gauge or up-down counter takes its declared keys. Passing `error.type` to a histogram does not compile. An in-flight count is incremented and decremented inside the helper's `instrument(op, fn)` `try`/`finally`, never bare in a handler.

| Backend                  | Adapter                                                                                                                                                              |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| none yet                 | in-memory recorder: arrays of observations and increments, zero dependencies                                                                                         |
| OpenTelemetry            | a `Meter` with a `Histogram` (explicit bucket boundaries) and a `Counter`; `UpDownCounter.add(delta, attrs)` and synchronous `Gauge.record(value, attrs)` for levels |
| Google Cloud Monitoring  | an OpenTelemetry `MeterProvider` with the OTLP or Cloud Monitoring exporter, `exportIntervalMillis: 60000`                                                           |
| Prometheus               | a `prom-client` registry with a `Histogram` and a `Counter`, label names fixed at construction; `Gauge.set`/`inc`/`dec` for levels                                   |
| Datadog                  | `distribution(name, seconds, tags)` for durations, `increment(name, 1, tags)` for failures and `gauge(name, value, tags)` for levels                                 |
| Workers Analytics Engine | `env.<DATASET>.writeDataPoint({ indexes: [op], blobs: [outcome, errorType], doubles: [seconds] })`; a level goes in a double the same way                            |

## Test recipe

| Backend                  | How the emission test observes the write                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| none yet                 | assert on the in-memory recorder's arrays; for a gauge, the last `set` value                                                               |
| OpenTelemetry            | an in-memory metric reader or exporter, then collect and assert on the data points; for a gauge, the last recorded value                   |
| Google Cloud Monitoring  | an in-memory metric reader, same as OpenTelemetry                                                                                          |
| Prometheus               | inspect the registry (`registry.getMetricsAsJSON()`) and assert on the sample labels; for a gauge, the sample value                        |
| Datadog                  | inject a spied client and assert on the call arguments; for a gauge, the `gauge` call's value                                              |
| Workers Analytics Engine | no in-memory exporter exists: pass a spied dataset binding and assert on the `writeDataPoint` argument; for a level, the double holding it |
